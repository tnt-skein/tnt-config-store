# Правка конфигурации кластера

`tnt-config-store` — правка конфигурации кластера Tarantool 3.x, которая
не роняет кластер: сверка правки с действующей топологией, раскатка
в три фазы — проверить у всех, записать один раз, дождаться, — правка
по кускам, разница без паролей, история ревизий в etcd и функции, которыми
узел отвечает раскатке.

```lua
local rollout = require('tnt.config.rollout')

local result = rollout.apply({
    current = current,              -- что применено сейчас
    patch = { { path = 'app.cfg.limit', value = 100 } },
    revision = stored.revision,     -- запись пройдёт только поверх этой ревизии
    targets = { 'storage-001-a', 'storage-002-a' },
    validate = validate, write = write, applied = applied,
})

result.phase     --> 'converge': кандидата приняли все, записан одной транзакцией
result.pending   --> {}: каждый узел доложил, что применил новую ревизию
diff.describe(result.changes[1])   --> 'изменено app.cfg.limit: было 50, стало 100'
```

Зависит от [`tnt-async`](https://github.com/tnt-skein/tnt-async) (узлы
спрашиваются веером), [`tnt-clock`](https://github.com/tnt-skein/tnt-clock)
(сроки), [`tnt-collection`](https://github.com/tnt-skein/tnt-collection)
(порядок разделов и ревизий), [`tnt-context`](https://github.com/tnt-skein/tnt-context)
(перенос контекста в функции узла), [`tnt-external`](https://github.com/tnt-skein/tnt-external)
(подмена диска и ядра в проверках), [`tnt-fingerprint`](https://github.com/tnt-skein/tnt-fingerprint)
(контрольная сумма ревизии) и [`tnt-str`](https://github.com/tnt-skein/tnt-str)
(обрезка значения знаками). Клиент хранилища — например,
[`tnt-etcd-client`](https://github.com/tnt-skein/tnt-etcd-client) — пакет
получает аргументом, а не берёт сам.

## Зачем пакет

Схему конфигурации проверяет само ядро: неизвестное поле и неверный тип
оно отвергнет. Чего оно не проверяет — не сломает ли правка живой
кластер. А сломать можно молча, синтаксически безупречной правкой:

- **вычеркнуть узел.** Из кластера он не исчезает: остаётся в системном
  спейсе, портит статус репликации и однажды возвращается — с данными,
  о которых никто не знал;
- **перенести узел в другой репликасет.** Он придёт туда со своими,
  чужими для репликасета данными;
- **выдать двум узлам один адрес.** Один из них недостижим, и выясняется
  это в первый же обход кластера.

Согласованного применения в ядре тоже нет. Запись в общий источник каждый
узел применяет сам и когда придётся: половина кластера применила,
половина свалилась в alerts, а признака «все сошлись на этой ревизии»
не существует — есть только локальное состояние каждого узла. Битая
конфигурация при этом валит кластер веером: узлы применяют её по очереди
и падают по очереди, а откатывать уже некуда.

Пакет закрывает обе дыры и то, что вокруг них:

- **Проверка до записи — у всех.** Правку сперва сверяют с действующей
  топологией, никуда не ходя, затем кандидата смотрит каждый узел тем же
  разбором, которым ядро читает конфигурацию при старте, — и только
  потом она пишется.
- **Запись одна.** Одна транзакция, обусловленная прочитанной ревизией:
  правка, сделанная поверх чужой, не пройдёт, а расходиться записи
  нечему — либо она прошла, либо нет.
- **Схождение по докладу ядра.** Раскатка ждёт, пока каждый узел
  доложит, что применил записанную ревизию, и называет тех, кто
  не доложил, с причиной. Узел, прочитавший ревизию и упавший
  на применении, сошедшимся не считается.
- **Разница без паролей.** Оператор видит, что изменилось, по разделам,
  а пароль — фактом «изменился», не значением.
- **Правка по кускам.** Назвать место и то, что там должно оказаться;
  всё остальное, включая чужие правки, остаётся как было.

Модули пакета независимы, и фасада у него нет: раскатка идёт там, где
сидит оператор, а функции узла — на каждом узле, и тянуть одно в другое
незачем.

| Модуль | Что делает |
|---|---|
| `tnt.config.rollout` | раскатка в три фазы |
| `tnt.config.node` | ответы узла: проверка кандидата, доклад о применённом, запись файла |
| `tnt.config.topology` | сверка правки с действующей топологией |
| `tnt.config.patch` | правка по кускам |
| `tnt.config.diff` | разница по разделам |
| `tnt.config.secrets` | заглушки вместо секретов и их возврат |
| `tnt.config.history` | история ревизий рядом с конфигурацией |
| `tnt.config.file` | запись файла конфигурации без половинок |

## Как пользоваться

### Раскатка: `rollout.apply`

`rollout.apply(request)` берёт действующую конфигурацию, кандидата
и три функции приложения — проверить на узле, записать, спросить узел,
что он применил, — и возвращает итог. Функции пишет приложение: только
оно знает, где хранится конфигурация, как дойти до узлов и под какой
учётной записью. С функциями узла из `tnt.config.node` и клиентом
`tnt-etcd-client` они выглядят так (`uris` — адреса узлов с учётной
записью, которой выдано право на эти функции:
`maintenance:…@127.0.0.1:3301`):

```lua
local netbox = require('net.box')
local yaml = require('yaml')

local node = require('tnt.config.node')

--- Вызов функции узла; отказ связи — пара, а не исключение.
local function call(name, func, ...)
    local connection = netbox.connect(uris[name], { wait_connected = 2 })

    if not connection:is_connected() then
        return nil, ('узел %s не отвечает'):format(name)
    end

    local ok, answer = pcall(connection.call, connection, func, { ... })

    connection:close()

    if not ok then
        return nil, tostring(answer)
    end

    return answer
end

--- Фаза 1: узел смотрит кандидата, ничего не применяя.
local function validate(name, config)
    local check, err = call(name, node.FUNCTIONS.check, config)

    if check == nil then
        return false, err
    end

    return check.ok, check.err
end

--- Фаза 2: одна запись, пока ревизия в хранилище та же.
local function write(config, revision)
    local put, err = client:cas_cluster_config(yaml.encode(config), revision)

    if put == nil then
        return nil, tostring(err)
    end

    return tonumber(put.revision)
end

--- Фаза 3: что узел применил и что о себе говорит.
local function applied(name)
    local state, err = call(name, node.FUNCTIONS.applied)

    if state == nil then
        return nil, err
    end

    return state, state.err
end
```

Дальше — раскатка целиком присланного текста:

```lua
local stored = client:read_cluster_config()

local result = rollout.apply({
    current = yaml.decode(stored.value),
    candidate = yaml.decode(text),
    revision = stored.revision,
    targets = { 'storage-001-a', 'storage-002-a' },
    validate = validate,
    write = write,
    applied = applied,
})

result.phase       --> 'converge'
result.revision    --> ревизия, которую записали
result.converged   --> { 'storage-001-a', 'storage-002-a' }
```

Поля запроса:

| Поле | Что это |
|---|---|
| `current` | действующая конфигурация; без неё сверять топологию не с чем, и первая запись идёт без сверки |
| `candidate` | кандидат целиком — либо `patch` |
| `patch` | правки по кускам к `current` (ниже, «Правка по кускам») |
| `revision` | ревизия, поверх которой пишем; уходит вторым аргументом в `write` |
| `targets` | имена узлов, которых спрашивают |
| `removing` | узлы, которые выводят из состава намеренно |
| `instance` | имя узла, который сам применяет правку: вычеркнуть его нельзя |
| `validate(name, candidate)` | `true` либо `false, причина` |
| `write(candidate, revision)` | новая ревизия либо `nil, причина` |
| `refresh(name)` | необязательная просьба перечитать конфигурацию: `true` либо `false, причина` |
| `applied(name)` | доклад `{ revision, status, alerts }` либо `nil, причина` |
| `timeout` | срок схождения и каждой фазы, по умолчанию 30 с |
| `interval` | пауза между опросами схождения, по умолчанию 0,5 с |
| `monotonic`, `sleep` | часы; по умолчанию — `tnt-clock` |

Раскатка идёт по шагам и останавливается на первом отказе. На каком —
говорит `result.phase`:

| `phase` | Что случилось | Записано |
|---|---|---|
| `patch` | правка по кускам не собралась: путь с ошибкой или упирается в значение | нет |
| `unchanged` | кандидат совпадает с действующей: раскатывать нечего, все узлы уже там | нет |
| `topology` | правка ломает топологию (ниже, «Сверка топологии») | нет |
| `prepare` | кандидата отверг хотя бы один узел — или не ответил в срок | нет |
| `commit` | запись не прошла: например, ревизия в хранилище уже другая | нет |
| `converge` | записано; `pending` пуст — все применили, иначе названы отставшие | да |

Итог:

| Поле | Что это |
|---|---|
| `phase` | на каком шаге остановились |
| `changes` | разница кандидата с действующей — и при отказе тоже: оператор видит, что он раскатывал |
| `revision` | записанная ревизия; `nil`, если не записано |
| `converged` | узлы, применившие новую ревизию, по порядку имён |
| `pending` | узлы, не применившие её; при остановке до записи — все, при `unchanged` — никто |
| `states` | последний доклад каждого узла о себе |
| `errors` | причина по имени узла: возражение, молчание, провал применения, отказ перечитать |
| `err` | общая причина отказа; `nil`, если все сошлись |

Отказ до записи следов не оставляет: ничего не записано, и кластер живёт
как жил.

```lua
local refused = rollout.apply({
    current = current,
    candidate = broken,
    revision = stored.revision,
    targets = { 'storage-001-a', 'storage-002-a' },
    validate = validate,
    write = write,
    applied = applied,
})

refused.phase                     --> 'prepare'
refused.err                       --> 'конфигурация отвергнута узлами'
refused.errors['storage-001-a']   --> текст отказа ядра: Unexpected field …
```

Отказ на схождении значит другое: запись прошла, а часть узлов её ещё
не применила. Это не повод откатывать — это повод перечитать конфигурацию
на отставших; `errors` называет, почему каждый не дошёл:

```lua
result.phase                     --> 'converge'
result.pending                   --> { 'storage-002-a' }
result.err                       --> 'конфигурация записана, но применена не всеми'
result.errors['storage-002-a']
--> 'конфигурация не применена, ядро в состоянии check_errors: error: tx_binary: failed to bind, …: Address already in use'
```

Узел сошёлся, если доложил ревизию не меньше записанной и состояние ядра
`ready` или `check_warnings`. `check_warnings` — применено с замечаниями:
узел живёт на новой ревизии, а замечания лежат в `states`. `check_errors`
— не применено, какую бы ревизию узел ни назвал. Доклад без состояния
судится по ревизии.

Узлы спрашиваются веером, а не по одному: проверка, просьба перечитать
и каждый заход схождения идут ко всем разом, с одним сроком на фазу.
Молчащий узел задерживает фазу на один срок, а не каждый на свой.
Не ответивший в срок возражает (на проверке) или не докладывает
(на схождении) с причиной «узел не ответил в срок»; исключение в функции
приложения — такой же отказ, с текстом исключения.

**Просьба перечитать.** Там, где источник конфигурации сам за хранилищем
не следит, узел без просьбы останется на прежней конфигурации сколько
угодно долго. `refresh` зовётся после записи и до ожидания. Отказ на нём
раскатку не прерывает — узел вправе подхватить конфигурацию сам — и лишь
записывается в `errors`; у узла, который к тому же не сошёлся, там стоит
причина несхождения: она объясняет, почему раскатка не закончилась.

```lua
refresh = function(name)
    return call(name, 'config_reload')   -- своя функция узла: config:reload() под admin
end,
```

### Узел: `tnt.config.node`

Узел отвечает раскатке тремя функциями. Их публикует приложение, а право
на вызов выдаёт конфигурация — прав на данные для этого не нужно:

```lua
local node = require('tnt.config.node')

node.publish()   -- config_check, config_applied, config_write
```

```yaml
credentials:
  users:
    maintenance:
      password: '…'
      privileges:
        - permissions: [execute]
          lua_call: [config_check, config_applied]
```

Имена — `node.FUNCTIONS`; другие задаются аргументом:
`node.publish({ check = 'cfg_check' })`. Функции принимают перенос
контекста раскатчика последним аргументом (`context.accept` пакета
`tnt-context`) и снимают его до тела: проверка кандидата и доклад идут
на узле с `request_id` правки, которую затеял оператор.

**`node.check(candidate)`** смотрит кандидата, ничего не применяя,
тем же разбором, которым ядро читает конфигурацию при старте, и ищет
в нём себя по имени:

```lua
node.check(candidate)
--> { ok = true, instance = 'storage-001-a', declared = true, warnings = {} }

node.check(broken)
--> { ok = false, err = '[cluster_config] …: Unexpected field "опечатка"', declared = false, … }
```

Узел, которого нет в кандидате, не возражает — узлы выводят из состава
намеренно, — но предупреждает: после применения он перестанет быть
частью кластера, и знать об этом надо до записи.

**`node.applied()`** докладывает, что применено:

```lua
node.applied()
--> { status = 'ready', revision = 8, alerts = {} }
```

`status` — состояние ядра из `config:info('v2')`, `alerts` — его
замечания весом и текстом, `revision` — ревизия применённой, а не
последней прочитанной конфигурации: её ядро помнит за каждым источником,
который её рассказал (встроенный источник Enterprise, источник
[`tnt-ce-etcd`](https://github.com/tnt-skein/tnt-ce-etcd)). Источнику,
который ядру ревизию не рассказывает, приложение подставляет своего
поставщика — он отвечает за применённую ревизию, иначе раскатка сочтёт
сошедшимся узел, упавший на применении:

```lua
node.configure({
    revision = function()
        return source:applied_revision()   -- число либо nil, причина
    end,
})
```

Узел вне декларативной конфигурации докладывает `status = 'uninitialized'`
без ревизии и не сходится. Ядро, которое не знает ответа `v2`, — `err`
с его отказом: это ответ, а не падение узла.

**`node.write(text)`** — для кластера без хранилища: переписывает файл
конфигурации этого узла (ниже, «Файл конфигурации»). Путь задаёт только
приложение, а не аргумент: право позвать функцию по сети иначе было бы
правом переписать на узле любой файл. Перечитывает узел отдельной
просьбой — записать и применить решает тот, кто раскатывает.

```lua
node.configure({ path = '/etc/tarantool/cluster.yaml' })

node.write(text)   --> { ok = true, path = '/etc/tarantool/cluster.yaml' }
```

`node.configure` задаёт поставщика ревизии и путь разом; поле, которого
нет, сбрасывается.

### Сверка топологии: `tnt.config.topology`

Сверка смотрит на два документа и никуда не ходит, поэтому правку можно
проверить до того, как она куда-то поедет. Раскатка зовёт её сама первым
шагом; отдельно она нужна там, где правку показывают до раскатки.

```lua
local topology = require('tnt.config.topology')

local ok, objections = topology.acceptable(current, candidate)

ok   --> false
objections[1]
--> { kind = 'moved', target = 'storage-001-b',
--    message = 'узел storage-001-b переносится из storage-001 в storage-002; правкой конфигурации это не делается' }
objections[2]
--> { kind = 'address_taken', target = 'storage-001-b',
--    message = 'адрес 127.0.0.1:3301 объявлен и у storage-001-a, и у storage-001-b' }
```

Возвращаются все возражения сразу, а не первое: оператор видит всё и чинит
за один подход. `topology.validate` отдаёт только список.

| `kind` | Что не так |
|---|---|
| `removed` | узел вычеркнут, а в `removing` не назван |
| `moved` | узел переехал в другой репликасет |
| `regrouped` | репликасет переехал в другую группу |
| `address_taken` | два узла объявлены с одним адресом |
| `self_removed` | правка вычёркивает `self_name` — узел, который её применяет |

Вывод узла из состава объявляется явно: `{ removing = { 'storage-001-c' } }`.
Вычеркнуть узел и вывести его — разные вещи, и первое обычно случайность:
правку писали руками, и узел потерялся.

`topology.instances(config)` разворачивает три уровня конфигурации —
группы, репликасеты, узлы — в плоскую карту `имя → { name, replicaset,
group, uri }`; адрес — первый в `iproto.listen`.

### Правка по кускам: `tnt.config.patch`

Присланный целиком текст несёт с собой всё, чего оператор не трогал:
случайную правку соседнего раздела и прочитанное полчаса назад, поверх
которого с тех пор кто-то уже записал своё. Правка по кускам называет
место и то, что там должно оказаться:

```lua
local patch = require('tnt.config.patch')

local candidate = patch.apply(current, {
    { path = 'app.cfg.limit', value = 100 },
    { path = 'credentials.users.replicator.password', value = 'secret-2' },
    { path = { 'labels', 'app.kubernetes.io/name' }, value = 'orders' },   -- точка в имени — путь списком
    { path = 'app.cfg.legacy', remove = true },
})
```

- Путь — имена разделов через точку либо списком имён. Недостающие
  разделы заводятся.
- Списки заменяются целиком: номер элемента не адрес, вставка в начало
  сдвигает всё, что ниже, и правка по вчерашнему списку попала бы сегодня
  в чужой элемент.
- Удаление — отдельный признак `remove = true`, а не пустое значение:
  `nil` в таблице Lua неотличим от забытого значения. Правка без значения
  — отказ; `box.NULL` — значение, явный пустой раздел.
- Правки применяются по порядку и к копии: действующая не меняется,
  а отказ любой правки — отказ целиком, половинчатого кандидата не бывает.

```lua
patch.apply(current, { { path = 'app..cfg', value = 1 } })
--> nil, 'правка 1: путь app..cfg написан с пустым именем раздела'
patch.apply(current, { { path = 'app.cfg.limit.max', value = 1 } })
--> nil, 'правка 1: путь app.cfg.limit.max упирается в значение: app.cfg.limit — не раздел'
patch.apply(current, { { path = 'app.cfg.limit' } })
--> nil, 'правка 1: нечего положить по пути app.cfg.limit: значение не названо'
```

Раскатка собирает кандидата сама, если вместо `candidate` передан
`patch`: правка по кускам проходит те же фазы, что и целый текст.
`patch.get(config, path)` читает значение по пути, `patch.split(path)`
разбирает путь в список имён.

### Разница: `tnt.config.diff`

```lua
local diff = require('tnt.config.diff')

for _, difference in ipairs(diff.of(current, candidate)) do
    print(diff.describe(difference))
end
--> убрано app.cfg.legacy: было true
--> изменено app.cfg.limit: было 50, стало 100
--> изменено credentials.users.replicator.password: было [скрыто], стало [скрыто]
--> добавлено labels.app.kubernetes.io/name: orders
```

Разница считается по разделам, а не по строкам: переставленные ключи
и переформатированный YAML — не изменение. Находка — `{ path, kind,
before, after }`, `kind` — `added`, `removed` или `changed`; разделы
на каждом уровне идут по порядку имён, и список от вызова к вызову
не перетасовывается. Списки сравниваются и показываются целиком.
`box.NULL` — значение: раздел, объявленный пустым, отличается
от отсутствующего, как и `1` от `1LL`.

`diff.render(value)` пишет значение одной строкой: таблицу — JSON,
пустую таблицу — `{}`, отсутствие — «ничего»; длиннее 120 знаков
обрезается с многоточием — знаками, а не байтами. Сама находка значение
держит целиком.

### Секреты: `tnt.config.secrets`

В конфигурации лежат пароли всех учётных записей кластера, а её
показывают целиком: в панели, в разнице перед раскаткой, в выводе
инструмента. Оператору нужен факт «пароль изменился», а не значение —
по значению он ничего не решает, зато оно остаётся в истории браузера,
в журнале терминала и в почте, куда разницу переслали.

```lua
local secrets = require('tnt.config.secrets')

secrets.mask('etcd', { password = 'x', endpoints = { 'http://root:hunter2@127.0.0.1:2379' }, ssl_key_file = '/k' })
--> { password = '[скрыто]', endpoints = { 'http://root:[скрыто]@127.0.0.1:2379' }, ssl_key_file = '/k' }
```

Секрет узнаётся по имени раздела: имя равно `password`, `passwd`,
`secret`, `token`, `cookie`, `authorization` или `key` либо кончается
на одно из них через подчёркивание (`api_key`, `db_password`). Конец
имени, а не вхождение: политика паролей ядра — `password_min_length`,
`password_lifetime_days` — остаётся на виду, как и `ssl_key_file`:
путь к ключу не ключ. В адресе с учётными данными прячется только пароль:
по хосту и логину оператор понимает, куда переехал узел.

`secrets.hide(differences)` прячет секреты в найденной разнице; `diff.of`
зовёт его сам, последним шагом и безусловно. Последним — потому что
сравнение идёт по настоящим значениям: два «[скрыто]» равны, и смена
пароля выглядела бы отсутствием правки.

`secrets.restore(candidate, current)` — обратный ход, и без него прятать
нельзя вовсе: показанную конфигурацию оператор правит и присылает обратно
тем же текстом. Заглушки становятся настоящими значениями из применённой
конфигурации, пароль в адресе — тоже, а хост и логин остаются присланные:
переехать можно, не зная пароля.

```lua
local shown = secrets.mask('config', current)             -- показать
local restored = secrets.restore(edited_shown, current)   -- принять обратно
restored.credentials.users.replicator.password            --> 'secret-1'

secrets.restore({ app = { password = '[скрыто]' } }, current)
--> nil, 'заглушку нечем заменить: app.password — в применённой конфигурации на этом месте секрета нет'
```

Заглушка, которой нечем стать, — отказ, а не пропуск: записать её как
есть значило бы запереть учётную запись словом «скрыто». Так же отказывает
заглушка в адресе не на месте пароля.

### История: `tnt.config.history`

Раскатка не откатывается сама, но вернуться оператор должен уметь,
а для этого нужно хранить то, что было. Ревизии лежат рядом с самой
конфигурацией, в том же хранилище: отдельная база под историю — ещё один
отказ в момент, когда всё и так плохо. Клиент — любой с договором
`put`, `get`, `range_prefix`, `delete` клиента `tnt-etcd-client`:

```lua
local history = require('tnt.config.history')

history.record(client, { revision = 8, config = candidate, author = 'admin', comment = 'лимит 100' })   --> true

history.list(client)[1]        --> { revision = 8, checksum = '…', author = 'admin', comment = 'лимит 100', config = { … } }
history.get(client, 8).config  --> конфигурация ревизии 8
history.get(client, 5)         --> nil: такой ревизии нет
history.prune(client)          --> 0: убирает всё сверх последних двадцати
```

Раскатка историю не пишет: хранилище ей не известно, запись — дело
`write`, и `history.record` ставится туда же, после удачной записи.

- Ключ — `history/<номер>` относительно префикса клиента, номер дополнен
  нулями до двадцати знаков: хранилище отдаёт ключи по порядку строк,
  и без выравнивания десятая ревизия встала бы между первой и второй.
- Ветка истории — не под `config/`: встроенный источник Enterprise
  читает всю ветку `config/` и сливает её ключи в конфигурацию, и запись
  истории стала бы там неизвестными полями.
- Каждая запись несёт контрольную сумму конфигурации (`tnt-fingerprint`).
  `get` считает её заново и отказывает, если запись побилась: вернуть
  кластер к битой конфигурации хуже, чем не вернуть вовсе.
- `list` отдаёт ревизии новыми первыми и пропускает записи, которые
  не разобрать; `prune(client, keep)` оставляет последние `keep`,
  по умолчанию `history.KEEP` — 20.

### Файл конфигурации: `tnt.config.file`

Кластер, поднятый из файла, иначе правится только руками на каждом узле.
`file.write(path, text)` пишет файл так, чтобы половины не осталось:
во временный файл рядом (`.new`), сброс на диск, прежнее содержимое —
в сторону (`.bak`), переименование поверх. Сброс до переименования
обязателен: без него файл появится на месте, а содержимое — когда-нибудь
потом, и переживший отключение питания узел поднимется на пустом файле.

```lua
local file = require('tnt.config.file')

file.write('/etc/tarantool/cluster.yaml', text)    --> true
file.read('/etc/tarantool/cluster.yaml.bak')       --> прежнее содержимое
file.write('/нет/такого/cluster.yaml', text)       --> false, 'файл /нет/такого/cluster.yaml.new не создан: …'
```

`.bak` — не резервная копия, а последняя конфигурация, на которой узел
точно поднимался, и нужна она в тот единственный час, когда новая
не поднимается. Отказ записи оставляет прежний файл нетронутым
и временный — убранным. Права нового файла — `0640`: в нём пароли всех
учётных записей кластера, и читают его владелец и группа, а не все.

## Чем пришлось поступиться

**Отката нет.** Узел, не применивший новую конфигурацию, чинится
перечитыванием, а не возвратом всего кластера к прежней ревизии: возврат
— ещё одна правка, и валить ею кластер второй раз незачем. Вернуться
можно руками — раскатить прежнюю ревизию из истории как кандидата,
через те же три фазы.

**Фаза проверки требует согласия всех целей.** Недоступный узел —
возражение, и раскатка на кластер с лежащим узлом остановится на `prepare`.
Узел, выведенный из работы, приложение убирает из `targets` само
и осознанно: раскатка не знает, кого можно не спрашивать.

**Атомарна запись, а не применение.** Одна транзакция в хранилище
не делает применение одновременным: между первым и последним узлом
кластер живёт на двух конфигурациях. Раскатка это не прячет, а делает
видимым — `pending` и `errors`.

**Файлы атомарности кластеру не дают.** `file.write` атомарен на узле,
но узлов много и файлов столько же: раскатка по файлам защищена проверкой
на всех узлах до записи и докладом после, а не атомарностью. Где нужна
одна точка записи, ставят хранилище. Ревизии у файла нет вовсе, и без
поставщика ревизии (`node.configure({ revision = … })`) раскатка
по файлам не сойдётся.

**Проверка кандидата — внутренним модулем ядра.** Узел проверяет
кандидата `internal.config.cluster_config` — тем же кодом, которым ядро
читает конфигурацию при старте. Модуль не объявлен публичным договором
Tarantool и может меняться между выпусками; своя проверка расходилась бы
с настоящей ровно там, ради чего проверка заводится, и это дороже.

**Сверка топологии смотрит на текст адреса.** `127.0.0.1:3301`
и `localhost:3301` для неё разные адреса; учитывается первый адрес
`iproto.listen`, остальные — нет.

**Секреты узнаются по имени и по виду адреса.** Пароль под именем,
которое на секрет не похоже, уйдёт в разницу как есть; имя сомнительное
прячется — лишняя заглушка стоит оператору вопроса «а что там было»,
утечка стоит кластера.

**Работа с деревом, а не с текстом.** Правка по кускам и возврат
заглушек собирают кандидата из разобранного YAML, и записанный обратно
текст теряет порядок ключей и комментарии. Кому они важны, пишет
в `write` присланный текст, а не дерево, — там, где текст был.

**История хранит пароли.** С заглушками к ревизии было бы не вернуться,
поэтому ветке истории в etcd нужны те же права, что и ключу конфигурации,
и выдаются они отдельно: доступ к ветке `config/` историю не покрывает.
